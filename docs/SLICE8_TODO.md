# Slice 8 — Let a delegated operator save subgoals under one parent

An owner can ask “Break my Go chess game into subgoals and save them for review.” The operator reads the current plan, chooses useful skills and decides how many children to create, what each should achieve, and how success could be checked. The owner can later start at the parent goal and trace each saved child to the operator, grant, run and call that created it.

## Owner and operator contract

- [x] Add `operator goal grant-subgoals PARENT_ID OPERATOR_ID` as a thin owner command. Extend the existing definition-grant model with the action `create_subgoal` scoped to that parent. Reuse `operator ask --definition-grant GRANT_ID` and `operator goal withdraw-definition-grant GRANT_ID`. One grant permits repeated creation of direct children. Creating grandchildren requires a grant on their immediate parent.
- [x] Expose one audited MCP write, `create_subgoal(parent_goal_id, expected_parent_revision, retry_key, title, …definition fields)`. Use the existing goal fields for criteria, measurement and timing. For this operation, require `success_criteria` to be a string containing non-whitespace text. The operator judges its substance. Each successful new creation saves one child at revision 1 with status `draft` and returns its ID, revision and status. Derive operator and grant from the recorded session. Handle the action explicitly in both the `operator ask` launcher and MCP tool registration. A parent-granted run exposes `create_subgoal` as its sole write. Advisory sessions can propose the same plan in their reply.
- [x] Keep planning decisions with the operator. It can reread the tree, consult skills, save children individually, or ask the owner for missing information. A saved child is a goal definition. Worker assignment, skill handoff to workers and workload execution belong to a later slice.

## Model and audit

- [x] Put the write in one public `GoalAPI` operation callable from plain Python. Reuse the existing goal insertion, definition validation, creation retry and revision-attribution machinery. Inside one transaction verify the open run and call, the exact active grant, the owner-visible parent and its expected revision. For a new key, allow creation under a draft, active or paused parent. Return a conflict for a completed or revoked parent. Apply this lifecycle rule inside the delegated creation transaction. Save the child, parent link, retry record and committing-call link together. Creating siblings leaves the parent revision and status intact.
- [x] Scope each retry key to its grant. A new call with the same key, parent revision and definition returns the original child creation result and records a retrieval. Validate the grant, target and expected parent revision before honoring a retry. If the parent has since completed or been revoked at the same revision, an exact retry still retrieves the existing result. Include parent ID and expected parent revision in the subgoal request fingerprint alongside the child definition. After a parent revision changes, the original request is stale. Resubmitting the same key and definition against the new revision conflicts with the stored request identity. Preserve the existing fingerprint for top-level creation. The operator can inspect the tree and history to see what already committed before deciding how to proceed. A withdrawn grant denies the old session even after the owner grants the same operator fresh authority.
- [x] At MCP call start, map `parent_goal_id` to `target_goal_id` and `expected_parent_revision` to `target_revision`, including on denied attempts. Record this parent pair as the **request target**, and the child ID and revision as the **committed or retrieved result**. Preserve a commit link even if the response is interrupted. A denial records the attempt with no child or commit. Use existing goal-visibility rules for linking attempts to timelines. The parent activity endpoint must expose the creation call, and the child’s first revision must point back to its original committing call. Run history already identifies any skill revisions listed or read.
- [x] Limit Slice 8 schema work to fresh workspaces. Define the grant and tool constraints in the shared [schema.sql](../packages/harness_api/src/harness_api/schema.sql). Populate acceptance workspaces from this snapshot. For the interruption test, reopen the same database.
- [x] Document the owner command and grant scope in [CATALOG.md](../CATALOG.md) and [TERMINOLOGY.md](../TERMINOLOGY.md). Show how to follow the parent request target to the committed child revision in the [HTTP activity contract](../README.md#operator-activity).

## Acceptance

**Offline.** Use temporary SQLite workspaces and real model operations. Keep adapter tests focused on tool discovery, argument mapping and recorded results.

- [x] Save two siblings under one grant against the same parent revision. Cover each allowed parent status and reject missing, empty and whitespace-only criteria. Complete the parent between calls without changing its revision. Verify a fresh key conflicts and an exact retry retrieves the first child, with its original committer. Cover the same outcomes for a revoked parent.
- [x] Revise the parent after the first child commits. Replay the original request and verify a stale-revision conflict. Then use the current parent revision with the same key and definition and verify a key conflict. Withdraw the grant and regrant it to the same operator. Verify the old session is denied on both a retry and a new key. Check the tree and audit after each attempt.
- [x] Exercise the launcher with a parent grant and inspect MCP discovery and direct invocation. Only `create_subgoal` is advertised as a write. Direct `revise_goal` is denied. Advisory and top-level creation sessions omit `create_subgoal` from discovery and deny direct invocation. Use the parent grant to attempt creation under a different parent and under an existing child. Check that each denial records the requested parent and revision and has no committed child.
- [x] Exercise concurrent identical retries, a changed definition under the same key, and a second attempted write through the same call. Verify one child and one original committer. Force failure while saving the commit link and verify rollback. Separately interrupt after commit and before reply recording, reopen the workspace, find the saved child, and retrieve it through a fresh authorized call. These cases distinguish a partial plan from a partially saved child.

**Signed in.** In a fresh CLI workspace, create “Build a chess game in Go” and register an operator. Use this same request in two fresh sessions. Keep IDs, tool names, skill names and expected child titles out of the prompt.

> Break my “Build a chess game in Go” goal into subgoals and save them for review. For each subgoal, say how we could tell it was done.

1. Capture the workspace goal IDs before the advisory session. Check that the reply proposes subgoals, the set of workspace goal IDs is unchanged, and the tree contains only the parent.
2. Issue the parent grant and repeat the request in a delegated session. Check that it saves multiple direct draft children with concrete success criteria. Let the operator choose their count, titles, order and skill reads.
3. From a fresh process, start at `GET /goals/{parent_id}/history?view=activity`. Follow creation calls to `GET /runs/{run_id}`. Compare the set of all newly created workspace goal IDs with the run’s committed child IDs and the IDs of the parent’s direct children. Inspect each saved child’s success criteria. Follow revision 1 at `GET /goals/{child_id}/history?view=activity` to the exact committing run and call sequence. Check the registered operator, grant and requested parent revision, and confirm parent status and revision are unchanged. Use durable records for these checks so a persuasive reply alone cannot pass.
