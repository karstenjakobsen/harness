# Slice 4 — Trace operator runs from a goal

Starting with a goal ID, an owner or web client should be able to find the runs that listed, read or targeted that goal, inspect what each call returned, and identify the call that committed a decision. A review that leaves the goal open should be discoverable after the process exits. Capture covers Harness MCP tool calls during `operator ask`. Direct CLI and HTTP reads are outside that scope. An observation entered through the CLI appears in goal history with its submitter and timestamp even when it has no associated run. Machine checks follow this slice. [Slice 4 discussion](SLICE4.md)

## Implementation

- [ ] **Start and finish each run through the public Python API.** The launcher obtains a stable run ID in the selected workspace and passes it to Harness MCP in the same workspace. Record UTC timing and distinguish success, failure and an unfinished run. Identify advisory sessions explicitly. For delegated sessions, bind the registered operator and exact grant from trusted startup context. The run ID identifies history. Completion authority comes from the grant. [Session launcher](../packages/harness_operator/src/harness_operator/codex.py)
- [ ] **Persist each call attempt before execution.** MCP identifies the tool and its requested target where applicable. The model durably records the run ID, call sequence, start time, tool and target before dispatch or denial. MCP identifies references in the actual result and the model records them with the known outcome. An interruption can leave a call unfinished, independently of the run outcome. A denied call retains its target and denial outcome even when it returns no resources. [Harness MCP tools](../packages/harness_mcp/src/harness_mcp/server.py)
- [ ] **Capture what each tool exposed.** Use typed relationships and stable IDs as specified below. Preserve empty results. History must report the revision, status and references returned at the time of the call, even after another observation or revision arrives.
- [ ] **Link the committing call in the model.** In `GoalAPI.complete_goal`, recheck the exact grant, target and revision on every attempt. Save the call’s link to the decision’s `event_id` in the transaction that saves the decision, citations and goal status. A rollback leaves the previously persisted attempt with no committed change. If the process dies after commit and before reply delivery, history still identifies the committing call. Mark any unknown call outcome as unfinished. An identical authorized retry has its own call entry identifying the decision it retrieved and preserving the original committing call. [Completion operation](../packages/harness_api/src/harness_api/models/goals.py)
- [ ] **Preserve attribution.** Store IDs, times, order and outcomes. Keep prompts, raw tool arguments and responses, and credentials out of activity records. Resolve the rationale and citations from the decision and the submitter and timestamp from each observation. A plan suggested only in a reply has no saved revision. For an operation that saves a plan, the references identify the resulting goal IDs and revisions. The operator chooses whether to act, and Harness records its calls automatically.
- [ ] **Upgrade workspace storage.** Update the fresh schema and add the upgrade from v8 in `WorkspaceDatabase`. Retain the supported upgrade from v7. Reopen a populated upgraded database and verify that goals, revisions, grants, observations, decisions and citations keep their IDs and relationships. Leave run attribution empty for records created before tracking began. [Schema snapshot](../packages/harness_api/src/harness_api/migrations/001_initial.sql) · [Upgrade policy](../AGENTS.md#schema-changes)

### What a goal’s history can say about a call

| Tool | Requested target and returned references | Relationship shown for the goal |
|---|---|---|
| `list_goals` | Capture each returned goal ID, revision and status, including results of an unfiltered list. | Appeared in a list. |
| `get_goal_tree` | Keep the requested root ID and each returned goal’s ID, revision and status. For a nested completion, retain its `event_id`, cited `evidence_ids` and `statement_evidence_id` when present. | Requested directly or appeared as a descendant. The call saw a decision citing the identified observations. |
| `get_goal_progress` | Keep the requested goal ID, assessed revision, returned status and exact observation IDs from `evidence`. | Requested directly. This call returned the observation records. |
| `complete_goal` | Keep the requested goal ID and expected revision, including on denial. Identify a committed decision or a decision retrieved on retry by its event ID and citations. | Targeted for completion. The outcome and decision link show what happened. |

### History reads for the CLI and web UI

- [ ] **Implement two owner-scoped model queries.** The goal query returns a chronological timeline of revisions, observations, decisions and related calls, including read-only runs. Each call entry identifies its run, sequence, time and typed relationship to this goal. The run query returns run identity, operator and grant when applicable, timing, outcome and ordered calls with targets, returned references and decision links. Use stable IDs and a deterministic order when timestamps coincide. Enforce owner scope in both model operations.
- [ ] **Ship both reads over HTTP and Click.** Controllers call the public model queries, views define typed JSON responses, and Click calls the same queries and formats their results. A web client can follow the IDs directly. Document both HTTP reads and the CLI commands together with coverage and attribution. [Goal controller](../packages/harness_api/src/harness_api/controllers/goals.py) · [HTTP views](../packages/harness_api/src/harness_api/views/goals.py) · [HTTP API](../README.md) · [Command catalog](../CATALOG.md) · [Terminology](../TERMINOLOGY.md)

| Read | HTTP | CLI |
|---|---|---|
| Goal timeline, including related run IDs | `GET /goals/{goal_id}/history?view=activity` | `operator goal history GOAL_ID` |
| One run and its ordered calls | `GET /runs/{run_id}` | `operator run show RUN_ID` |

The existing `GET /goals/{goal_id}/history` returns a list of revisions. Use the explicit activity view on that route for the timeline. Preserve the default revision-list response, `GoalAPI.get_goal_history` and `operator goal show GOAL_ID --history` for their current callers. [HTTP contract tests](../packages/harness_api/tests/test_http.py)

## Acceptance

- [ ] **Tool relationships, offline.** Use an advisory run to list goals, read a parent tree containing an already-completed child, then read the child’s progress. In the child’s timeline, verify the list appearance, the descendant returned from the requested parent and the direct read. Compare the tree’s decision ID and citations with the saved completion. Only the progress call should report observation records returned. Exercise a filtered list that omits the child.
- [ ] **Durability and authority, offline.** Reopen the workspace at three boundaries. An interruption after the attempt is saved leaves an unfinished call. A forced rollback preserves the attempt and leaves the goal open. An interruption after commit and before delivery preserves the decision and its committing call. Retry under the active grant and verify two calls reference one decision. Withdraw the grant and verify a denied attempt still identifies the targeted goal and has no committed event.
- [ ] **Model and adapter contracts, offline.** Test chronological and per-run ordering, owner scoping, and the same typed facts through Python, HTTP and Click. Cover the existing HTTP revision-list response, fresh and upgraded workspaces, and the exclusion of raw payloads from activity storage.
- [ ] **Signed in, review twice under the same grant.** Reuse the gym fixture. On each run, omit `--trace-file` and ask “Review this goal. If you judge the evidence sufficient, complete it. Otherwise tell me what’s missing.” [Delegated acceptance fixture](../packages/harness_operator/tests/test_goal_plan_live.py)

  1. Record the tour and day-pass receipt, then run the first review. From a fresh CLI process, find the run through `operator goal history` and inspect it with `operator run show`. Verify it returned the child’s revision and those two observation IDs, made zero completion calls, and left the child `active`. The reply identifies active membership as unconfirmed or asks whether the owner joined.
  2. Record the owner’s confirmation of active membership and repeat the request. Find a distinct run that read the new observation and committed exactly one completion. Follow its decision ID to the rationale, the registered operator and grant, and the citation identifying the owner’s confirmation. The child is `completed` and the parent is still `active`.
  3. Query both histories again in fresh CLI processes. The first run still lists only the two observations it received. The second links to the same decision shown in the goal’s revision history.

- [ ] **Discover both runs using only HTTP.** After both reviews, start the API against the same temporary workspace. Starting with only the child goal ID, request its activity timeline and follow the two returned run IDs to `GET /runs/{run_id}`. Assert on the JSON fields. The first progress call returned exactly the tour and day-pass IDs. The second returned those two plus the owner’s confirmation. Follow the second run’s committing call to its decision, assessed revision, registered operator, grant, rationale and citations. Resolve the cited confirmation’s submitter and timestamp in goal history. Reading the first run again must still return the original two IDs.
