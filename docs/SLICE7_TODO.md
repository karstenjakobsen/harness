# Slice 7 — Let an operator discover and read versioned skills

For the goal “Build a chess game in Go,” the operator chooses which skills to read and proposes subgoals in its reply. After the run, the owner can open the exact instructions each read returned. Saving proposed subgoals under a parent-scoped grant belongs to a later slice. [Slice 7 design](SLICE7.md)

## Implementation

- [x] **Ship the two skills.** Add `skills/chess-rules/` and `skills/go-testing/`, each with an `operator.yaml` manifest and a `SKILL.md`. Include `kind: skill`, a stable `id`, `name`, `description`, `author` and revision 1. In the chess skill, show how moving a pinned piece can expose its king. In the Go skill, show how to express a position, candidate move and expected legality as a table-driven test case.
- [x] **Import before each new `operator ask` session.** A small Git reader resolves one Harness commit independently of the caller’s working directory, then reads every manifest and its Markdown from that commit’s `skills/` tree. Pass the complete catalog, repository-relative paths and commit SHA to a public model operation that validates and stores the catalog in the selected workspace. Start the session after a successful import. Owner-scoped HTTP reads of runs and skill revisions use SQLite alone, including when the checkout is unavailable or its latest catalog is invalid.
- [x] **Enforce revision integrity in the public model.** Use the manifest ID as identity across folder moves. Store each snapshot under `(id, revision)` with both files, their content hash, source path and commit SHA. Reimporting identical content preserves the original snapshot and provenance, including after an unrelated commit. If either file changes under the same key, reject the entire import with the skill ID, revision and an instruction to bump the revision.
- [x] **Define discovery by the last successful import.** In one transaction, save new revisions and replace the set of discoverable ID and revision pairs with those in the imported catalog. A higher revision in that catalog becomes discoverable. A removed skill disappears from `list_skills()`, while `read_skill(id, revision)` and earlier audit links still resolve its saved snapshots.
- [x] **Expose two audited MCP reads.** In recorded advisory and delegated sessions, offer `list_skills()` for current IDs, revisions, names and descriptions, and `read_skill(id, revision)` for the exact manifest, Markdown and provenance. Have both tools call public Harness API operations. Let the operator select skills from their descriptions. [MCP server and call recorder](../packages/harness_mcp/src/harness_mcp/server.py)
- [x] **Make both directions inspectable.** Use the existing recorder to save the call outcome and the skill revision references from the structured result before handing it to the transport. From `GET /runs/{run_id}`, distinguish versions listed from instructions returned and let the owner follow each read to an exact revision over HTTP. Expose an owner-scoped reverse lookup from that revision to the runs and call sequences that read it. A listing alone, a failed lookup and an unfinished call must each yield zero full-read references. A full read establishes only that Harness returned the instructions. [Run activity contract](../README.md#operator-activity)
- [x] **Upgrade storage and document the contract.** Extend the fresh schema and the upgrade from a populated v12 workspace. Reopen the upgraded database and verify existing runs, calls and returned references still resolve. Document the skill lookups, MCP tools and meaning of each audit reference. [Schema snapshot](../packages/harness_api/src/harness_api/migrations/001_initial.sql) · [Workspace upgrades](../packages/harness_api/src/harness_api/database.py) · [Command catalog](../CATALOG.md) · [Terminology](../TERMINOLOGY.md)

## Acceptance

- [x] **Offline, exercise the catalog across commits.** Use one temporary Git repository and a separate empty workspace.

  1. Import both skills at revision 1 twice, then import again after an unrelated commit. Verify one snapshot per skill with its original SHA. In a recorded run, list both skills and read only `chess-rules` revision 1.
  2. In a single commit, bump `go-testing` to a valid revision 2 and change the chess instructions under revision 1. Verify the import rejects the commit with the chess ID, revision and bump message. Discovery must still list both at revision 1, exact lookup of Go revision 2 must fail, and chess revision 1 must retain its original content. With the invalid commit still checked out, open the saved run over HTTP and follow its read to the original chess instructions. Repeat the conflict check with a manifest-only chess edit.
  3. Bump the changed chess skill to revision 2 and import the corrected catalog. Verify discovery lists both skills at revision 2. Commit and import the removal of `chess-rules`. Verify discovery now lists only Go revision 2 and `read_skill("chess-rules", 1)` still returns the original instructions.
  4. Make the checkout unavailable and reopen the workspace. Follow the original run’s read over HTTP and compare its manifest, Markdown, path, SHA and hash with the original chess snapshot. Follow chess revision 1 back to the original reading call. Verify that Go revision 1, which the run only listed, has no reading runs.

- [x] **Signed in, prove the operator can choose skills and propose a plan in an advisory session.** In an empty workspace, create the goal with `operator goal create --title "Build a chess game in Go"` and record its ID and original revision. Start a fresh advisory `operator ask` with this question. [Live acceptance fixture](../packages/harness_operator/tests/test_goal_plan_live.py)

  > For my ‘Build a chess game in Go’ goal, what subgoals would you propose, and how would you verify that a move cannot leave your own king in check?

  Check the structured results for discovery and full reads of both seeded revisions. Check that the reply proposes subgoals and gives a concrete chess position and a Go test with the correct expected result. For example, with White’s king on e1 and rook on e2, Black’s rook on e8 and king on a8, and all other squares empty, White’s e2–f2 exposes its king and must be rejected. Accept equivalent positions, wording and read order. Starting from the saved run, follow both full reads over HTTP and match the returned instructions and provenance to the revisions the operator read. Fetch the goal tree by its saved ID and assert that the goal still has its original revision and zero children.

- [x] **Offline verification.** `make check` and the type check of all three source packages passed. `make test` passed all 177 offline tests with warnings treated as errors. Coverage includes Git object provenance under local overrides, rollback of a mixed or ambiguous catalog, reopening a populated v12 upgrade, rejection of invalid audit references, and following a historical read over HTTP without Git.
- [x] **Signed-in verification.** `make test-live` passed all seven scenarios with warnings treated as errors. The chess scenario also passed a separate rerun with the final answer checks. The chess run read revision 1 of both seeded skills and proposed four subgoals. Its table-driven Go test expected `e2f2` to be illegal and `e2e3` to be legal. Both reads resolved over HTTP to the instructions returned by MCP. The saved goal stayed at revision 1 with zero children.
