# Slice 3 — Record progress and explain it

An owner should be able to ask “What progress have I made, and how do we know?” and get an answer that cites the records behind it. Slice 3 gives two examples with different answers. A food goal counts distinct days. A standing file-permission goal reports the condition at the latest check. Both can stay `active` as evidence arrives. [Slice 3 discussion](SLICE3.md)

## Proposed design

Record evidence once under the stable goal ID and remember the revision in force at submission. Source adapters report observations. The model assesses them against the revision’s criteria, CLI and MCP return that result, and the assistant explains it using the cited records. The evidence-write and progress-read names and signatures in the slice notes are provisional. [Proposed operations](SLICE3.md#proposed-operations) · [Engineering guidelines](../AGENTS.md#definitions-and-state)

Start with two kinds of structured criteria. The food criterion specifies a target number of distinct days and which reports qualify. Keep that target separate from `duration_days`, which already describes the time window. The file criterion specifies a source, path and expected octal mode. A goal with prose-only criteria can still show its evidence and report that automatic assessment is unavailable.

## Implementation order

- [ ] **Decide how historical progress works before implementing that read.** Suppose revision N ends Monday night and a qualifying report about Monday arrives Tuesday. Evaluating N with today’s evidence includes that report. Reproducing what Harness knew on Monday excludes it based on its recording time. Document the chosen contract, define the cutoff if needed, and use this case as its model test. Under either choice, a saved completion keeps its original revision and exact evidence citations. [Open design decision](SLICE3.md#open-decision-for-historical-progress)
- [ ] **Define attribution for each evidence entry point.** Derive the submitter from caller context the application can establish. `ADMIN_USER_ID` identifies the workspace account, a resource ID selects the target, and `owner_user_id` identifies the owner. An HTTP request carrying those values can still have an unknown initiator. Record the requester of a check and the observer that produced its result separately when known. Mark each unknown identity explicitly. [Identity and attribution](../TERMINOLOGY.md#identity-and-attribution)
- [ ] **Store evidence and its audit details.** Add an observation kind to `goal_events` and use the event ID as the stable evidence ID. Store what was reported, its source, its attribution and when Harness recorded it. For food, store the calendar date the report concerns. For a machine check, retain the check time, outcome and any observation time supplied by the source. Give submissions a retry key so a repeated request returns its original ID, while two intentional reports for Monday receive different IDs.
- [ ] **Preserve completion and workspace data.** Extend `complete_goal` with optional evidence IDs alongside the existing confirmation or reference. In one transaction, verify the current revision and that all cited records belong to this goal, store the confirmation or reference with its recorded provenance, link the decision to its evidence, and change status. An identical retry returns the saved decision. A stale revision or conflicting retry leaves every record untouched. Give legacy completion evidence a stable ID exactly once. Test a fresh workspace and upgrades from v5 and older supported versions. Reopen the upgraded workspace and verify the historical decision ID, source, timestamps, public fields and evidence links. [Schema policy](../AGENTS.md#schema-changes) · [Schema snapshot](../packages/harness_api/src/harness_api/migrations/001_initial.sql) · [Workspace upgrade code](../packages/harness_api/src/harness_api/database.py)
- [ ] **Implement the agreed reads.** Return the assessed revision, goal status, result and cited records. Group qualifying food reports by their reported day and retain every supporting ID. For the file, return the latest check outcome and the last successful observation with their timestamps. Expose revision creation times and evidence submission times through goal history. Reading progress or recording evidence leaves lifecycle status unchanged. [Proposed operations](SLICE3.md#proposed-operations)
- [ ] **Collect file evidence.** Add an owner-triggered check against a configured container interface. Fetch outside the database write transaction with a bounded timeout. Validate the source, path and mode before recording a machine observation. A dedicated endpoint may also establish the condition through HTTP 200 if its configured contract explicitly guarantees that condition. Record that basis. A generic health response, malformed payload or timeout yields `unknown`. Preserve the last observed mode. An owner-pasted link retains owner-supplied provenance.
- [ ] **Wire the agreed public operations.** Proposed workspace commands are `operator goal observe`, `operator goal check` and `operator goal progress`. Extend `create` and `revise` for the criteria and `complete` for repeatable evidence IDs. Click parses arguments and displays the API result. HTTP views define schemas and controllers map model results and errors. Only the collector can submit machine-sourced observations. Expose progress through read-only MCP. Update the catalog and glossary with the implemented contracts. [Catalog](../CATALOG.md) · [Glossary](../TERMINOLOGY.md)

## Acceptance

| Scenario | What the tests must prove |
| --- | --- |
| Food log | Prove the Monday example through the public Python model first. Then exercise it through the CLI and operator, checking the count, both citations, attribution, and active status. Verify that history shows when the reports arrived and when the target changed. [Monday acceptance example](SLICE3.md#proposed-monday-acceptance-example) |
| Attribution | An HTTP write with a known goal owner and no established caller keeps the submitter unknown. An owner-pasted app link keeps its owner-supplied provenance. A separate check requested by a known user and answered by the app identifies that user as requester and the app as observer. |
| Standing file mode | Serve the actual mode of a temporary file from a local HTTP fixture. Observe `0600` at 10:00 (`met`), change the file to `0644`, and observe it at 10:05 (`unmet`). Require the operator to cite both observations and place the change after the first check and by the second. Time out the 10:10 check. Require `unknown` for the latest check, `0644` at 10:05 as the last known mode, and `active` throughout. Use a controlled clock for exact times in deterministic tests and the captured timestamps in the live test. |

- [ ] Test two evidence IDs on one decision, stale revisions, retries and rejection of evidence from another goal. After recording a completion, add a later report and revise the goal. Verify that the saved decision still cites exactly its original evidence. Test HTTP and CLI field mapping and error handling at their public entry points.
- [ ] For each of the food-log and standing-file live tests, create a temporary workspace and database, populate it through the installed CLI, and run `operator ask`. Assert a successful MCP progress read for the captured goal ID, check the structured result, then check the facts and citations in the answer. Keep expected facts out of the question. Clean up the database, trace, temporary file and server on success and failure. [Existing live test](../packages/harness_operator/tests/test_goal_plan_live.py)
- [ ] Run `make check`, `make test` and the separately invocable, signed-in `make test-live`. Report the live result explicitly. A skipped live test leaves slice acceptance pending.
