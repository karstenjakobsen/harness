# Slice 3 — Let an operator decide when to complete an assigned subgoal

The next assignment gives a registered operator authority to complete **one assigned subgoal** using evidence already in Harness. The owner delegates the action. The operator judges whether the evidence is sufficient and can ask a question or leave the goal open. Review that decision end to end before resuming the 3B file check. [Slice 3 revisit](SLICE3_REVISIT1.md)

## Agreed decisions

- Harness preserves reports, their sources and their timestamps. A tool can supply an exact fact such as the number of distinct dates covered. The operator interprets those facts against the owner’s goal. A status change requires an explicit, authorized model operation.
- Use the revision’s existing `success_criteria` and `measurement_plan` to describe in plain language what evidence would suffice and how to obtain it. The operator may propose wording or revise it when authorized. The completion grant alone permits only completion. For example, “confirmation of active membership is sufficient” is a criterion. The owner’s later confirmation is a separate observation with its own ID, source and time.
- `get_goal_progress(goal_id, revision=N)` applies revision N’s criteria to the evidence available now. A saved completion retains the revision and exact evidence IDs cited when the decision was made. [Historical progress](SLICE3.md#historical-progress)
- Evidence and decisions have separate authors. If the owner confirms an active membership and the operator decides to complete the goal, history must identify the owner as the source of the confirmation and the registered operator as the decision maker. [Identity and attribution](../TERMINOLOGY.md#identity-and-attribution)

- [x] The model records owner-supplied and unattributed evidence with stable IDs, provenance and retry handling. Progress exposes every record considered and groups qualifying IDs under each reported date. New future-dated reports are rejected.

## Delegated completion

This increment adds one delegated action through one public completion operation. Recording evidence leaves the goal open for review. A status change occurs when an authorized caller requests completion.

- [ ] **Delegate, withdraw and bind.** Let the local owner grant and withdraw completion authority for one subgoal and a registered operator they own. Bind the session in trusted startup code to that specific grant. Use the database-generated assignment ID as the grant ID by closing the assignment on withdrawal and creating a fresh row on each new grant. Even for the same operator and goal, the replacement grant requires a new session. Ordinary advisory and drafting sessions retain their read-only tools. [Assignment schema](../packages/harness_api/src/harness_api/migrations/001_initial.sql) · [Session launcher](../packages/harness_operator/src/harness_operator/codex.py)
- [ ] **Expose one MCP write.** Offer `complete_goal(goal_id, expected_revision, evidence_ids, rationale)` in the delegated session. Derive the actor from the binding. Map `expected_revision` to the existing model revision argument. The tool returns the saved decision. Keep the assistant’s shell sandbox read-only.
- [ ] **Steer the bound session.** Give it the assigned outcome and the action the owner delegated. Instruct it to read the current revision and cited records, weigh their provenance, ask for clarification when useful and explain any decision. Keep the existing advisory instructions for ordinary sessions. The host controls tool exposure and the model enforces the grant on each call. [Current operator instructions](../packages/harness_operator/src/harness_operator/codex.py)
- [ ] **Enforce authority in the model.** Extend `GoalAPI.complete_goal` so all callers share the transition. In one write transaction, check the operator is still registered, the delegation is active for that exact subgoal, the revision is current and the goal can be completed. Require a nonblank rationale and at least one existing observation from that goal. Interpreting what those observations establish belongs to the operator. [Current completion operation](../packages/harness_api/src/harness_api/models/goals.py)
- [ ] **Save a decision from existing evidence.** Atomically record the operator’s integer ID, goal, revision, decision time, rationale and exact citations with the status change. Both the MCP result and history must identify who made the decision and why, and let the reader trace each cited statement to its original submitter and timestamp. Adapt the storage constraint that requires every completion to have a new statement. Preserve the existing owner and HTTP completion contracts. [Schema policy](../AGENTS.md#schema-changes)
- [ ] **Define retries and failures.** Recheck the session’s exact grant inside the transaction before writing or returning a saved decision. While that grant and revision are current, an identical retry returns the original decision. Compare citation IDs as a set. A conflicting retry, stale revision, withdrawn grant or invalid citation leaves history and status intact. Completion affects only the assigned subgoal. The owner retains authority over the parent’s desired outcome.

### Acceptance

1. **Model and adapters, offline.** Use a temporary workspace. Prove success, identical retry, conflicting retry and rollback through the public model. Try an unassigned sibling, the parent, a different operator, an operator unregistered after session start, a stale revision, and missing or foreign evidence. From advisory MCP, attempt both discovery and direct invocation of the write. From delegated MCP, attempt to supply an actor ID. Verify each denied call leaves state intact and a successful call returns the decision later read from history.
2. **Withdraw and regrant, offline.** Open a session under grant A. Withdraw A while the operator stays registered and verify its next completion call is denied. Grant the same action on the same subgoal to the same operator again. Before starting a new session, retry the valid request from the old one. It must still be denied, with the subgoal open and no decision recorded. Bind a fresh session to grant B and verify the same request succeeds.
3. **Judgment, signed in.** Through the installed CLI, create an active parent and the subgoal “Get a gym membership.” Register an operator and delegate completion once. Record the owner’s account of a member’s tour and a reference to a day-pass receipt. Use “Review this goal. If you judge the evidence sufficient, complete it. Otherwise tell me what’s missing.” verbatim on both reviews. On the first review, the trace shows the evidence read and zero completion calls. The child stays open and the reply identifies the missing evidence.
4. **Execution, signed in.** Record the owner’s explicit confirmation of active membership and repeat the request under the same grant. Verify the MCP completion result cites that confirmation and attributes the rationale to the operator. Reopen history and verify who supplied the statement, who decided it was sufficient, and that only the child was completed. Keep the tour, receipt and confirmation in the fixture. The production prompt and model operation must work for a library membership or another goal without edits. ## 3B — Optional machine checks, deferred

Start after reviewing delegated completion. Keep the existing `one_time` and `standing` goal kinds. An operator with the appropriate grant can choose an available check and when to invoke it. The check’s contract determines exactly what its result establishes. [File-check example](SLICE3.md)

- [ ] **Configure the revision.** Add an optional reference to the workload and named check. A `one_time` revision can explicitly authorize completion on a passing result. By default, a pass records evidence and leaves the goal open. A `standing` goal records each result and stays active.
- [ ] **Collect the observation.** Start with a local HTTP fixture that reads a temporary file’s actual mode. Capture the revision, workload, check, target path and expected mode before fetching outside the write transaction. Record who requested the check, which adapter observed the result, and when. Keep Nomad workload lookup and HTTP details inside the adapter. A dedicated endpoint’s HTTP 200 establishes `0600` only when its contract guarantees that mode for that file. A generic health endpoint’s 200 establishes reachability.
- [ ] **Apply the authorized outcome.** For a trusted pass on an opted-in, still-current revision and target, use the same `GoalAPI.complete_goal` operation as delegated completion. The model applies the revision’s instruction directly. Save the named check and its observation ID as the basis for completion in history. An unmet or unknown result records the check outcome and leaves the goal open.

### Machine-check acceptance

| Fixture | Expected result |
| --- | --- |
| One-time file goal, passing check | With completion on pass enabled, a single decision cites the machine observation. Replaying the result returns the saved decision. With the option off, the same pass records `met` and leaves the goal active. A generic health 200 cannot complete the file-mode goal. |
| Standing file goal, repeated checks | `0600` at 10:00 gives `met`, `0644` at 10:05 gives `unmet`, and a timeout at 10:10 gives `unknown`. The goal stays active throughout. Progress cites both observations and retains `0644` at 10:05 as the last observed mode. |
| Revision changes during a one-time check | Hold a passing response for `/app/a`, revise the goal to `/app/b`, then release the response. Keep it as evidence for the original revision and target. The revised goal stays active and has no qualifying observation for `/app/b`. |
