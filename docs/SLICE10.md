# Slice 10 — Give a Nomad worker a scoped, auditable brief

An owner asks an operator to prepare Go test cases for a saved chess subgoal. The operator chooses a worker profile, writes a brief, and pins the skills the worker can read. Harness starts one Nomad worker. The worker submits a test fixture against the exact goal revision, and the operator reviews what it establishes. The goal stays open until an authorized completion decision.

AI Team's registry also provides defaults, modes, prompts, workflows, scripts, integrations, runtime adapters, collections, and distribution. The companion guide maps the full catalog and package structure to Harness use cases. Slice 10 puts one package through a real operator-to-worker handoff first. ## Skills, plugins, profiles and grants

Use AI Team's manifest-based packaging and its separation of agent instructions from executable workflow steps. In Harness, a plugin release groups reusable material. The public models enforce grants, and the execution backend starts and inspects the worker.

| Concept | Slice 10 contract |
| --- | --- |
| Skill | Keep `SKILL.md` as the instruction format and move metadata into the owning plugin manifest. Reuse the existing audited MCP reads and `SkillAPI` query semantics. A worker sees the exact skill revisions assigned to its work item and reads them through scoped MCP calls. Record assigned revisions and full reads separately. |
| Plugin | Use a Git-backed `plugin.yaml` with an ID, positive integer `revision`, descriptive metadata, skill definitions, profile paths and result-format schemas. Import the declared files from one committed tree. Publish the catalog atomically after validation. Save the manifest, source commit and digest so historical references survive upgrades and removal from discovery. |
| Role profile | Give each profile file a role of `operator` or `worker`, short instructions and references to skills in its plugin release. A worker profile names its declared result format. Identify a profile by plugin ID, plugin revision and profile ID. Use one optional operator profile on `operator ask --profile` and pin one worker profile on the work item. A registered operator keeps its own identity and grants when it uses a profile. |
| Grant | The owner authorizes one registered operator to delegate work against one saved goal. The operator session binds that exact grant. Harness issues a separate worker grant bound to one work item and one authenticated execution attempt. Declaring a capability in a plugin or profile conveys no authority. |

## Catalog layout

Use `registry/plugins/` as the canonical package source tree. The manifest owns skill metadata, references YAML files under `profiles/`, and registers result schemas under `schemas/`. Skill instructions live at `registry/plugins/<plugin-id>/skills/<skill-id>/SKILL.md`. Use the bundled `engineering` manifest and its declared files as the first catalog entry. Switch the importer and seed files together so the manifest replaces the root skill tree and per-skill `operator.yaml` files. Start in a fresh workspace for the new schema, as allowed by the local POC. [Example manifest](SLICE10/registry/plugins/engineering/plugin.yaml)

Resolve profile skill IDs to the exact revisions declared by that plugin release. Require globally unique skill IDs in the active catalog, valid profile roles, valid result schemas and regular UTF-8 files inside the package. Resolve schema references only from the pinned package and enforce a payload size limit before validation. Hash each normalized skill entry with its Markdown. Hash the manifest and all files it declares at runtime for the plugin release. Reject changes to an existing skill or plugin revision and keep prior snapshots in SQLite. The owner can remove a plugin from discovery while earlier work still resolves its saved snapshots. Harness selects the worker image by digest from its runtime configuration. Templates, references, and evaluations in the example support authoring. [Registry growth](SLICE10/REGISTRY.md#where-slice-10-fits)

## From operator request to worker result

1. **Save the work.** Add a goal-scoped work delegation grant and a single audited MCP operation to delegate one work item. The operator supplies the goal ID, expected goal revision, worker profile, brief, selected skill revisions and retry key. The public model rechecks the active grant, scope and current revision. In one transaction, save the immutable brief and pins, its first pending execution run and the operator call that committed them. An identical authorized retry retrieves that work item and run. A changed request under the same key conflicts. A second intentional attempt has a new execution run ID.
2. **Launch the run.** A host-side dispatcher starts the pending run through `ExecutionBackend` after the database transaction. Recheck the exact grant and goal revision before launch. Use the saved run ID and image digest on retries, including when registration may have succeeded before a timeout. Persist the job handle, observed allocations and execution outcome in Harness before Nomad removes its records. Keep Nomad configuration and API calls in the adapter.
3. **Bind the worker.** Use a short-lived Nomad workload identity with a Harness-specific audience. Verify its signature, issuer, audience and expiry against the configured cluster. Derive the task, namespace, job and allocation from the verified identity. Compare those values with the expected job and original allocation from the trusted backend. Issue a scoped worker session only after Harness has established that binding. Treat a replacement allocation or unresolved placement as ineligible. Keep the worker-facing MCP endpoint separate from the workspace owner's HTTP interface.
4. **Serve the brief and accept the result.** The worker-facing MCP session reads its brief, pinned goal revision, profile and assigned skills. Its sole write submits a bounded result for that work item. The model validates the pinned result schema, rechecks the active worker grant and exact attempt, derives worker attribution from the session, and atomically saves the observation, original goal revision and committing call. An identical authorized submission retry retrieves the original observation. A changed submission conflicts. If the owner revises the goal during the run, the submitted result remains evidence for the revision the worker was given. A revoked grant or revoked goal blocks the write. [Worked example result](SLICE10/registry/plugins/engineering/examples/king-safety.json)
5. **Review the evidence.** Starting with a goal ID, an owner or fresh operator session can follow the activity to the work item, profile revision, operator grant and committing call, worker run, original allocation, skill reads and submitted observation. Report execution state and what was submitted as separate facts. The operator reviews the fixture against the saved criteria and can use the existing completion flow if authorized.

## Implementation order and acceptance

1. **Catalog and profiles.** Verify that a fresh workspace imports the committed plugin tree and that reopening it preserves the saved snapshots. Cover duplicate IDs, missing references, invalid role values and edits without a revision bump. Publish a newer release and show that an earlier work item still resolves its original skill and profile revisions.
2. **Model and MCP contracts.** Test scoped operator delegation, atomic work-item and run creation, stale revisions, same-key retry and rollback. Prove that an advisory operator cannot delegate. From worker MCP, test discovery and direct calls for an assigned skill, an unassigned skill, an expired or withdrawn grant and a different work item. Prove that a retry preserves the first committing call and that a result submitted after a goal edit keeps its original revision.
3. **Nomad handoff.** On a disposable cluster, prove that the expected original allocation can authenticate and a valid identity for a different or replacement allocation cannot. Run the chess scenario with one real worker and inspect the result over HTTP starting with the goal ID. Check the pinned profile and skills, exact skill reads, structured test cases, execution outcome and operator-side review. Keep the goal open and verify that the result is attributed to the worker. Run `make check`, `make test`, signed-in `make test-live` and `make test-nomad` for the implementation and capture the evidence per the repository guidelines.
