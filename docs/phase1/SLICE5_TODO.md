# Slice 5 — Delegate and audit goal creation and revision

An owner can ask a registered operator to save a goal definition, then ask it to revise that goal. Starting with the goal ID, a web client can identify the exact run and call that committed each revision. The operator can also ask for clarification or propose a change in its reply. Machine checks, evidence collection and carrying out the goal are outside this slice. [Slice 5 discussion](SLICE5.md)

## Baseline before Slice 5

- `GoalAPI.create_goal` saves a goal and its first revision. `GoalAPI.update_goal` appends a revision when the definition changes. The revision operation currently has no expected-revision check, and activity links committing calls to completion decisions only. Reuse the definition logic and add the delegated authority check and revision link in the write transaction. [Goal model](../../packages/harness_api/src/harness_api/models/goals.py)
- A standalone MCP process can currently expose `complete_goal` with a completion grant and no run ID. Require a recorded, grant-bound run for every MCP goal write, including completion. The server records Harness MCP calls during `operator ask`. The launcher requests a read-only sandbox, which still permits workspace file reads outside the MCP trace. The trace is stored in the workspace database and can be altered by a process with database write access. [MCP server](../../packages/harness_mcp/src/harness_mcp/server.py) · [Session launcher](../../packages/harness_operator/src/harness_operator/codex.py)
- The timeline bug where a denied call could attach to a goal created later with the same ID is already addressed in `debcc23` (schema v10). Preserve goal resolution at call start and extend the regression to the new writes. [Activity regression](../../packages/harness_api/tests/test_run_activity.py)

## Authority and tools

Use separate grants for the two actions. A creation grant allows repeated creation of top-level goals in the owner's workspace while the grant is active. A revision grant covers one named goal, selected by its stable ID. The owner can grant revision of a newly created goal once its ID exists. The owner approves each grant once. Harness rechecks the grant on every call. Creating subgoals through MCP requires a parent-scoped creation grant in a later slice.

| Grant | Owner command | MCP write available in the bound session |
| --- | --- | --- |
| Create a top-level goal | `operator goal grant-create OPERATOR_ID` | `create_goal(title, retry_key, …definition fields)` |
| Revise one goal | `operator goal grant-revision GOAL_ID OPERATOR_ID` | `revise_goal(goal_id, expected_revision, …definition changes)` |

Reject reuse of a call reference that already has a committed or retrieved revision, even while the call is `unfinished`.
